# Momo Authentication

Parent: [[Momo Public Readiness]]. Boundary: [[Momo Backend Security]].

The backend validates JWT signature, supported algorithm, pinned issuer/audience, expiry, issued-at, authenticated role and UUID subject. Token-provided key URLs do not choose the JWKS endpoint. It accepts only signed Supabase identities whose provider is Google and authentication method is OAuth; anonymous, password and other-provider identities fail. Server keys never belong in the mobile client. Development identity requires explicit local/test flags.

The mobile code contains Google PKCE and secure session persistence with refresh/revocation/account-switch guards. User reports Google OAuth configured in staging, but no real account, redirect, refresh or native journey was exercised. AUTH-01 remains a release blocker. Public staging JWKS metadata contains one ES256/EC verification key; no user token was used in this check. Sign-in is verified by Supabase Auth; each API call verifies the signed Supabase JWT without a live Google/Auth round-trip. If Google disables an account after token issuance, that JWT can remain usable until its Supabase expiry or revocation; this follows the user's selected policy.

`GET /api/me` reads verified token identity and stored profile facts; unknown names/avatars are null. Migration 014 adds Google-only Auth-to-`public.users` profile sync and backfills existing Google users. It sources email from `auth.users`, sanitizes display-only metadata, rejects unsafe avatars, and avoids cross-binding on email collisions. The trigger installs before the backfill so concurrent Auth writes are serialized through commit. Local PostgreSQL tests cover these paths and Auth deletion cascade; the migration is applied to staging, but managed GoTrue execution remains unverified.

The local AUTH-02 account-deletion slice adds `DELETE /api/me`, which uses only the verified JWT subject with Supabase Auth Admin and safely handles a retry after deletion succeeded but its response was lost. The mobile asks for destructive confirmation, signs out, and clears only that account's SQLite records. Auth foreign-key cascades retire upload tickets; they do not themselves delete object bytes. The user confirmed pre-ticket originals were in Supabase `documents`; migration 015 records that destination and indexes retired legacy cleanup; it is applied to staging, where there were no legacy tickets to map. Full managed Auth behavior, physical Storage purge and old object-version removal are unverified, and inventory gaps remain a release blocker. Migration 014/015 are applied to staging; managed trigger behavior and physical Storage deletion remain unverified. Ordinary source deletion must preserve generated study material; account deletion is separate.

Dependencies: [[Momo Database]] ENV-02 -> real-account AUTH-01 -> AUTH-02 -> release device QA-01. AUTH-02 local profile provisioning and deletion exist; staging migration 014/015 are applied, while managed Auth execution, physical original-object cleanup and logout/account-switch device proof remain. Use synthetic users and notes only in an approved bounded staging smoke; never load/stress test production. See [[Momo Backend Completion 2026-10-14]].
